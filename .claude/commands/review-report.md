---
description: 產生給外部 code review（Claude Project 架構師）看的異動報告
---

針對本次尚未 commit 的變更，產生一份給外部 reviewer（不熟悉這次實作過程、只看得到規格書的架構師角色）看的異動報告。目標是讓 reviewer 不需要额外來回問就能判斷邏輯正確性，同時避免把不需要判斷的樣板/視覺類內容灌爆報告。

## 產生規則

### 1. 修改的既有檔案
一律附完整 unified diff，不論改動大小。每個檔案前簡述改動意圖一句話。

### 2. 新增檔案：先分類再決定揭露程度

**核心決策邏輯類**（符合以下任一條件即歸此類，附完整內容）：
- 包含事件訂閱、事件分派、或跨模組協調邏輯
- 包含條件判斷/分支邏輯，且該邏輯直接對應規格書裡描述的某個行為要求
- 是資料轉換層（把一種資料格式/來源轉成另一種）
- 是規格書裡提到的「可調參數」或「可擴充資料驅動」設計的實際承載者

**支援/樣板類**（一行描述即可，不附內容）：
- UI View/Controller 且不含業務判斷邏輯（純顯示、純綁定）
- Prefab、美術/動畫參數 SO
- 純資料容器（無邏輯的 struct/class）

若不確定某檔案該歸哪一類，歸入「核心決策邏輯類」（寧可多附，不要漏判）。

### 3. 場景/Prefab 異動
用結構化條列描述「新增了什麼節點、掛了什麼元件、跟既有哪個節點有從屬關係」，不要貼 YAML diff。

### 4. 單向依賴自我檢查（必寫）
列出這次新增的模組訂閱了哪些既有系統的事件；並反查這些既有系統的原始碼，確認沒有任何一個反過來 import 或參照新模組。若有反向依賴，必須明確標出並說明理由。

### 5. 事件替代聲明（必寫，若無則寫「無」）
若任何一個判定邏輯訂閱的事件，不是規格書原文指定的那一個，而是用語意相近的其他事件代理，必須在此明確列出：原規格指定的事件是什麼、實際訂閱的是什麼、為什麼判斷兩者語意等價。不得在報告其他段落裡不聲明就直接替換。

### 6. 輪詢檢查（必寫）
明確聲明這次異動有沒有新增任何 `Update()` / `FixedUpdate()` / 逐幀比對邏輯。若有，說明必要性；若無，直接寫「無新增輪詢」。

### 7. 已排除項目
列出被還原、不進這次 commit 的雜項異動（例如 Build 產生的專案設定檔異動）。

## 輸出格式

整份報告用一個標題清楚的 Markdown 結構輸出，方便使用者直接複製貼到外部對話。不要在報告最後加上「看起來符合規格」之類的自我評價語句——這是留給外部 reviewer 判斷的，不是這份報告該做的事。
