# 0004. 存檔系統採用自訂 JSON 格式，而非單純依賴 PlayerPrefs

## 狀態

已採用

## 背景

DeskSlayer 有多類需要跨遊戲階段保留的資料：最高分數、天氣城市選擇、武器背包與合成進度，以及音量、滑鼠偵測開關等使用者偏好設定。這些資料的重要程度差異明顯——偏好設定遺失，玩家重新調整即可；但武器背包或最高分數遺失，會直接影響玩家對遊戲的信任。這個差異決定了持久化方案不能只採用單一標準。

Unity 內建的 `PlayerPrefs` 在 Windows 上實際寫入登錄檔（Registry），只支援 `int`、`float`、`string` 三種基本型別，無法表達陣列或巢狀物件，也沒有版本控制機制。資料格式一旦調整，沒有機制讓舊資料相容新版本。這些限制決定了它只適合裝置端的輕量偏好設定，不足以承載「玩家會在意遺失」的資料。

## 決策

依資料性質分流至兩種持久化方案：裝置端偏好設定（音量、滑鼠偵測開關）維持使用 `PlayerPrefs`；結構化且需長期保留的資料（最高分數、武器背包與合成進度、天氣城市選擇）改用寫入 `Application.persistentDataPath` 的自訂 JSON 檔案，並在檔案中加入 `saveVersion` 欄位，供未來格式調整時的相容處理使用。

序列化工具選用 Unity 內建的 `JsonUtility`，未引入 `Newtonsoft.Json`。武器背包資料的實際結構是一份扁平清單，`JsonUtility` 搭配一個 wrapper class 即可處理，沒有必要為此新增外部依賴。每筆武器紀錄僅保留 `weaponId` 與 `synthesisLevel`，武器的靜態數值不重複儲存——這些數值屬於 ScriptableObject 資產，本身無法直接序列化，讀檔時以 `weaponId` 反查資料庫取回對應資產參照。

開發全域滑鼠輸入系統期間，原規格沿用既有做法，暫以 `PlayerPrefs` 存放滑鼠偵測開關與音量設定，作為正式存檔系統落地前的過渡方案。實作階段中途改為直接寫入正式 JSON 格式，原因是武器背包的存檔格式雛型當時已經確立，讓新設定直接掛入正式格式可省去後續一次資料遷移工程。

## 後果

正面影響：需長期保留的核心資料具備版本控制能力，未來格式調整不會導致既有存檔直接讀取失敗；序列化方案維持最小依賴，未引入非必要的外部套件。存檔系統作為橫跨多個模組的基礎設施，其設計從一開始即涵蓋防禦性讀寫考量（例如寫入過程遭中斷時避免產生損毀檔案）。

負面影響：`gameSettings` 區塊中途從過渡方案改為正式格式，代表 `mouseAttackInputEnabled`、`masterVolume` 兩個欄位在後續正式設計存檔系統規格時已成為既定輸入，須納入格式相容性考量，而非可重新規劃的空白畫布。此外，天氣城市選擇資料目前仍留在 `PlayerPrefs`，與其餘已遷移資料處於不同持久化狀態，尚待後續統一收斂。
