# 0002. 桌面透明視窗整合：從手刻方案到第三方套件

## 狀態

已採用

## 背景

DeskSlayer 的核心產品定位要求遊戲視窗完全透明疊加於桌面，玩家能在使用電腦的同時看到遊戲內容。這項需求涉及 Windows 系統層級的視窗合成機制，需要在專案初期評估手刻實作與採用第三方套件兩條路線的可行性與成本。

## 決策

**Spike 分支驗證手刻方案**：使用 `WS_EX_LAYERED` 搭配色鍵去背，並鎖定 D3D11 圖形 API，驗證手刻 Win32 方案的技術可行性。驗證過程中發現 Unity 6 預設採用的 D3D12 Flip Model 會導致色鍵去背完全失效，此為必須鎖定圖形 API 版本的直接原因。

**正式整合階段改採第三方套件**：進入正式整合階段後，需求範圍擴大至多螢幕支援、UI 自由拖曳、點擊穿透判定。評估這些擴充需求在手刻路線下的額外工程量，對照剩餘開發時程的風險，改採第三方套件 UniWindowController 完成正式整合。Spike 分支驗證過程中取得的圖形 API 相容性知識予以保留，分支本身不合併入主線。

**點擊穿透邏輯自行實作**：套件內建提供兩種點擊穿透判定模式，官方文件標註效能較重。改為自行實作三層優先序 Mediator：UI 優先可互動、其次為 `Collider2D` 可拖曳範圍、其餘一律穿透，取代套件內建模式。

## 後果

正面影響：採用成熟第三方套件大幅降低了多螢幕與點擊穿透這類邊界情境的處理成本，讓開發資源集中在遊戲玩法本身；Spike 分支驗證取得的圖形 API 知識即使分支未合併，仍實際影響了正式整合階段對相容性問題的判斷。

負面影響：正式整合依賴外部套件的實作細節與長期維護狀態，套件本身的效能特性（包含已知在特定顯示模式下產生的額外 GPU 成本，詳見 CPU 效能優化決策文件）並非完全在專案控制範圍內，後續仍需要額外的優化介入。
