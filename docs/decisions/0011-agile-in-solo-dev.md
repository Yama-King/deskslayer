# 0011. 敏捷精神實踐：單人開發下的時間盒與迭代增量

## 狀態

已採用

## 背景

敏捷開發的常見理解，容易停留在特定儀式的執行——每日站會、正式的 Sprint 回顧會議、故事點數估算。這些儀式在多人團隊裡有其存在理由，核心作用是同步資訊、協調分工。單人開發的情境下，這些協調性質的儀式不存在對應的實際需求，若機械式套用，只會產生沒有實質溝通對象的形式化流程。

專案在規劃階段需要決定：既然團隊規模是一人，是否仍有理由採用敏捷方法論，以及應該採用哪些部分。

## 決策

專案採用敏捷方法論的核心精神，而非其儀式層面。具體實踐包括：

**時間盒排程**：整個開發週期劃分為四週（W1 底層引擎、W2 視覺回饋、W3 系統擴充、W4 收尾），每週有明確的範疇邊界。

**迭代增量交付**：每個 feature branch 對應一個可獨立驗證的垂直切片，功能完成即可實際運行測試，不累積成一次性的巨大變更。

**持續整合**：每個分支完成後即進行 commit、發起 PR、合併回主分支，不讓多個未完成的功能同時堆疊在多個分支上。

**擁抱變化**：遊戲設計文件（GDD）隨實作進度動態更新，而非在專案初期一次性鎖定所有規格，後續嚴格禁止調整。

同時，明確不採用敏捷框架中屬於團隊協調機制的儀式部分：每日站會、正式的 Sprint 回顧會議、故事點數估算。這些機制的存在目的是同步多人之間的資訊落差與協調分工優先權，單人開發沒有對應的實際需求，若強行執行，僅是形式上模仿敏捷團隊的外觀，並未取得敏捷方法論真正想解決的問題。

## 後果

正面影響：時間盒與迭代增量讓四週的開發進度保持可視化與可控——W1 於第四天即完成，讓後續週次有餘裕評估並追加原規劃外的功能（武器收集、天氣系統）。持續整合避免了功能開發到後期才發現整合衝突的風險。

負面影響：省略正式儀式意味著沒有强制性的定期回顧機制，專案進度與方向的檢視依賴開發者本身的自律，而非外部流程強制。這個做法在單人開發下可行，但若團隊規模擴大，仍需要重新導入對應的協調機制，本次的取捨並非適用於所有團隊規模的通用結論。
