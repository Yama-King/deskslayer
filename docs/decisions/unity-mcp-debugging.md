# Unity MCP 連線除錯：定位 Windows 應用程式沙盒導致的路徑不一致

## 背景

專案採用 Claude Code 透過 Unity MCP（Model Context Protocol）操作 Unity Editor，用於讀寫場景、腳本與 Prefab。依官方文件完成 Unity 端套件安裝與設定後，Unity 端顯示連線狀態正常。然而 Claude Code 端無法搜尋到任何對應工具，且未顯示任何錯誤訊息。

## 排查過程

第一階段排查伺服器啟動狀態，確認伺服器實際上尚未啟動，Unity 端顯示的連線狀態與實際運作狀態不一致。手動啟動伺服器後，狀態確認正常，但 Claude Code 端仍無法搜尋到工具。

第二階段排查傳輸協定是否匹配（stdio 與 HTTP 兩種模式）。確認雙方協定設定一致後，排除此可能性。

第三階段搜尋是否為已知問題，找到一則描述相同症狀的 GitHub Issue：伺服器狀態顯示正常，但主控端完全無法搜尋到工具。討論串中有使用者指出問題與應用程式的安裝方式相關，進而確認本機的 Claude Desktop 為 Microsoft Store 版本。

Store 版本應用程式運作於 Windows 的 MSIX 封裝沙盒環境，該機制會將應用程式的檔案讀寫重新導向至與應用程式外部路徑不一致的實際位置。Unity MCP 寫入設定檔的路徑與 Claude Desktop 實際讀取設定檔的路徑因此並非同一位置，兩端各自對不存在交集的檔案進行操作。

透過 Claude Desktop 官方介面的「Edit Config」功能確認實際讀取路徑，證實與 Unity MCP 寫入位置不符。將設定內容手動複製至正確路徑後，重新整理，四十餘項工具正常列出。

## 結論

此次問題的根本原因並非任一端的設定錯誤，而是兩個獨立系統各自運作正常、卻對應到不同的實際檔案路徑，因此未產生任何錯誤訊息可供直接追蹤。此類問題需將排查方向從「設定是否正確」轉為「實際操作的路徑是否一致」，才能有效定位。

此案例也顯示 Windows 應用程式沙盒機制（MSIX/Store 封裝）在特定情境下會造成路徑重新導向，屬於平台層級的行為差異，未必會在一般開發過程中被注意到。後續遇到「設定顯示正常但功能無法連線」的情況，會將應用程式的安裝與封裝方式列入排查項目之一。
