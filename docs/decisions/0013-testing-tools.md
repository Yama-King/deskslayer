# 0013. 測試與除錯工具設計原則

## 狀態

已採用

## 背景

開發過程中陸續出現需要重複執行的測試情境：驗證存檔系統時需要反覆從全新狀態開始，驗證成就系統時需要重置已解鎖的成就進度。這類操作若每次都手動尋找存檔檔案路徑並刪除，除了耗時，也容易因為記不清正確路徑而誤刪其他檔案。

實作 `PlayStyleAnalyzer` 的分數統計邏輯時，另外發現一個獨立於工具設計本身、但同樣屬於測試範疇的問題：該模組自完成編寫後，從未被實際掛載到場景中運行過，也沒有其他系統讀取過它輸出的分數，代表這段邏輯僅通過了編譯，其正確性從未被實際驗證。

## 決策

在 Unity Editor 選單新增自訂工具項目，一鍵清除存檔檔案，取代手動尋找路徑刪除的流程。此類工具程式碼以 `#if UNITY_EDITOR` 包裹，確保僅存在於編輯器環境，不會被打包進最終發布的執行檔。

同時建立一個明確的判斷習慣：任何僅為了開發或測試方便而寫的程式碼（重置存檔、除錯用的資訊顯示等），撰寫當下即需一併決定它應該存在於哪些情境——僅限 Editor 環境、或連同測試用的 Development Build 也需要保留、還是必須在正式發布版本中完全排除。`UNITY_EDITOR` 為編譯期指令，判斷的是「是否在 Unity 編輯器中執行」；`Debug.isDebugBuild` 為執行期判斷，對應的是「打包時是否勾選 Development Build」，兩者是不同維度的情境旗標，可視實際需求疊加使用。

針對 `PlayStyleAnalyzer` 從未被實際驗證運行的發現，額外建立獨立的驗證測試，確認其分數輸出邏輯，並在過程中找出並修正了演算法本身的設計缺陷。

## 後果

正面影響：測試流程不再依賴手動操作檔案系統，降低了重複測試的時間成本與誤操作風險；明確區分「開發規格完成」與「邏輯已被驗證」兩種不同狀態，避免將編譯成功、規格書標記完成，直接等同於功能正確無誤。

負面影響：測試/除錯工具本身也是需要維護的程式碼，若專案規模持續擴大，工具數量增加後，這些工具本身是否維持在正確的情境限制下運作，也需要持續留意，並非一次性建立後即可視為完全解決。
