# 0007. 成就系統採單向訂閱架構，不修改任何既有核心系統

## 狀態

已採用

## 背景

成就系統需要監聽多個既有系統的行為以判定達成條件：敵人擊殺數、武器合成次數、按鍵觸發次數、攻擊次數、天氣事件等。這些來源分屬不同的核心系統（戰鬥判定、武器背包、輸入彙整層、天氣系統），若成就系統以直接呼叫或修改的方式取得資料，會讓這些原本互不相依的核心系統，額外背負「回報進度給成就系統」的責任，違反專案訂立的高內聚低耦合原則。

## 決策

成就系統以單向訂閱既有系統已公開的事件為唯一資料來源，不修改任何一個核心系統的內部邏輯或介面。數值累積型成就（例如累積打字量、累積擊殺數）採資料驅動設計，達成門檻定義在 ScriptableObject 資產中，新增門檻階段（例如追加更高等級的里程碑）僅需新建資產，不需修改程式碼。

實作結果驗證了五個核心系統（戰鬥判定、武器背包、輸入彙整層、天氣系統、敵人系統）在成就系統開發過程中未產生任何程式碼異動。

## 後果

正面影響：核心系統與成就系統之間僅存在事件訂閱這一種依賴方向，核心系統完全不知道成就系統的存在，未來新增或移除成就功能不會對核心系統造成回歸風險。數值型成就的門檻擴充成本降至新建資產，不涉及程式邏輯變更。

負面影響：單向訂閱架構要求核心系統在設計之初就公開了足夠細緻的事件（例如武器合成成功、特定天氣觸發），若既有系統未預先提供對應事件，成就系統將無法在不修改核心系統的前提下取得所需資料。此架構的可行性依賴於專案稍早已建立的事件驅動設計慣例，並非可以事後任意套用的通用解法。
