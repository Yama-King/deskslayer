# 0010. Git 版控實務

## 狀態

已採用

## 背景

專案全程採用 feature branch 開發模式，但單人開發下仍需要一套明確的判斷原則，決定什麼情況該切新分支、什麼情況該使用 Git Worktree，以及分支合併後的清理流程如何維持一致。

## 決策

**分支粒度**：以功能（feature）為單位開分支，命名採 kebab-case，對應單一份規格書的交付範圍。

**Worktree 使用時機**：判斷原則是「一次只做一件事」使用一般的切換分支；「主線工作進行到一半，同時需要處理插隊任務」才使用 Worktree。Worktree 讓硬碟上同時存在多份獨立的工作目錄，各自對應不同分支，避免 Unity Editor 在切換分支時因為場景／資產重新匯入而中斷正在進行中的工作狀態。

**PR-based 工作流**：每個 feature branch 完成後透過 Pull Request 合併，commit 訊息採 Conventional Commits 格式（例如 `feat:`、`fix:`、`chore:`），合併策略採 Squash and Merge，保持主分支的 commit 歷史精簡。

**分支清理**：合併後於遠端（GitHub 網頁）與本機（GitHub Desktop）分別手動刪除已合併分支。兩邊的分支清理是各自獨立的操作，遠端刪除不會自動同步至本機，反之亦然。

**版本追蹤範圍**：僅將實際會用到的檔案納入版控，素材包解壓縮後的授權文件、原始來源檔案、專案中未實際使用的其餘素材，不進版控紀錄。

## 後果

正面影響：Worktree 的判斷原則避免了在不需要的情境下引入額外的工作目錄管理成本，僅在真正需要平行處理任務時才使用；Conventional Commits 搭配 Squash and Merge，讓主分支的歷史紀錄本身具備可讀性，能夠不依賴額外文件、直接從 commit log 理解專案的演進脈絡。

負面影響：分支清理依賴手動執行且需要在兩處分別操作，若疏漏容易在遠端或本機累積已合併但未清除的分支，需要仰賴使用習慣的一致性，沒有自動化保障。
