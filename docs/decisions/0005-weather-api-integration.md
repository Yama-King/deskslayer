# 0005. 天氣 API 整合：選用 OpenWeatherMap 並建立容錯機制

## 狀態

已採用

## 背景

天氣連動戰鬥系統需要串接真實世界的天氣資料，作為外接 API 整合的技術實踐。市面上存在數個天氣資料 API 選項，其中部分服務（如 Open-Meteo）無需申請金鑰即可呼叫，整合門檻較低；OpenWeatherMap 則需要申請並管理 API 金鑰。

## 決策

選用 OpenWeatherMap，而非門檻更低的替代方案，理由是刻意練習完整的 API 金鑰申請與管理流程——包含金鑰的取得、儲存方式、以及避免將金鑰直接寫入版控歷史的處理方式，這是多數商業 API 整合情境下必然會遇到的實務環節，值得在此專案中實際操作一次，而非僅選擇技術門檻最低的路徑。

整合範圍涵蓋離線容錯（API 請求失敗或無網路時，戰鬥系統回退至預設數值，不影響核心玩法可用性）與快取節流（避免對同一城市在短時間內重複發送請求）。

天氣系統開發過程中，也發現既有的 `ICombatResolver` 介面簽章僅接受完整的 ScriptableObject 物件作為輸入，未預留讓外部數值（如天氣加成）介入戰鬥計算的參數空間。修正介面簽章以支援外部數值輸入，此修正視為對新功能所揭露的既有設計缺口進行補強，而非違反介面不應變更的開放封閉原則——新功能揭露既有設計的不足時，修正介面本身是必要的維護行為。

## 後果

正面影響：完整經歷了金鑰管理的實務流程，天氣系統具備離線容錯能力，API 服務不可用時不會導致核心玩法中斷。`ICombatResolver` 介面的修正也讓後續若有其他外部數值來源（不限於天氣）需要影響戰鬥計算，有現成的參數空間可以使用。

負面影響：API 金鑰的管理增加了專案的環境設定複雜度，本機開發與部署環境都需要正確配置金鑰才能讓天氣系統實際運作，若金鑰過期或超出免費額度限制，需要額外的監控與更新流程。
