# 0001. 介面化與解耦設計：戰鬥判定與輸入來源的邊界劃分

## 狀態

已採用

## 背景

專案訂立高內聚低耦合為核心架構原則，避免出現承擔過多職責的 God Class。這個原則在三處具體情境下需要落地為實際的程式設計決策：戰鬥傷害判定邏輯是否可能未來替換、輸入系統與敵人系統之間如何避免直接耦合、以及當輸入來源從單一鍵盤擴充為鍵盤與滑鼠兩種來源時，下游的戰鬥判定與統計系統是否需要因此增加對具體輸入來源的認識。

## 決策

**`ICombatResolver` 介面化**：戰鬥傷害判定邏輯（數值與機率式命中判定）以介面定義，具體實作可替換，不綁定單一計算方式。判定邏輯本身的呼叫方不需要知道背後是哪一種具體實作。

**`CombatDispatcher` 作為 Mediator**：輸入系統與敵人系統不直接互相參照，透過 `CombatDispatcher` 橋接雙方，避免兩個原本各自獨立的系統因為互相呼叫而產生耦合。

**`AttackInputAggregator` 統一輸入來源**：新增全域滑鼠輸入時，沒有讓下游的 `TypingEnergySystem`、`PlayStyleAnalyzer` 分別認識鍵盤與滑鼠兩種具體輸入來源，而是新增一層彙整層，將各輸入來源的原始事件統一轉換為單一格式的 `AttackInputData` 事件流。下游系統僅依賴這個彙整層，不直接參照任何具體的 Hook 類別。

彙整層的滑鼠偵測開關判定，刻意放置在下游分派這一層，而非 Hook 生命週期本身——滑鼠 Hook 是否運作，與這次輸入是否應該計入戰鬥判定，是兩個不同層級的問題，若將開關實作在 Hook 生命週期上，未來若有其他功能需要消費原始滑鼠事件，會被這個開關意外連帶影響。

## 後果

正面影響：三處解耦點各自降低了對應模組未來變更時的影響範圍。戰鬥判定邏輯可替換而不影響呼叫方；輸入系統與敵人系統的變更不會互相波及；新增第三種輸入來源（例如手把）時，僅需讓新來源產生對應格式的事件，`TypingEnergySystem`、`PlayStyleAnalyzer` 完全不需要異動。

負面影響：介面化與彙整層的抽象層本身增加了程式碼的間接層級，對於僅需要追蹤單一資料流向的除錯情境，需要多跳過一層才能找到實際的處理邏輯，屬於用間接性換取延展性的明確取捨。
